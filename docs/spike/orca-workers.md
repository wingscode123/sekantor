# Orca workers in SeKantor

Windows read-only spike, 2026-11-18. Orca's orchestration inventory sees structured Codex, Claude and Antigravity workers even when the PTY inventory is empty. The direct creator of a top-level structured worker was available in full dispatch context. The worker list and run list alone could not identify that coordinator. For the target pairing, exact dispatch lookups for the provider-populated Codex and Claude workers in `atap-arus` each resolved to one structured coordinator placement in `tower-trouble` via `worktree ps`. The target workspace also had 12 rows without provider metadata.

## CLI and joins

Paths below are inside the JSON `result` envelope unless specified. Identifiers are redacted to shape.

| Read-only command | Fields and observed behavior |
| --- | --- |
| `orca orchestration worker-list --json --full --limit 100` | `scope.source` was `all`, with 51 workers across two runs. CLI help says an implicit binding changes this to `bound`. Use an unbound poller and verify scope, or enumerate all runs and use explicit `--run <run_id>` (`flag`). Follow `page.nextCursor` while `page.hasMore`. `workers[]` includes supervised workers and may include context-only dispatches. |
| `orca orchestration dispatch-show --task <task_id> --json --full` | `dispatch.id = ctx_<hex>`, `task_id = task_<hex>`, `run_id = run_<hex>`, `assignee_handle = structworker_<uuid>`, `assignee_orca_session_id = <uuid>`, `process_incarnation = structured:<uuid>`, `creator_orca_session_id = claude_<uuid_with_underscores>` for this worker. `creator_dispatch_id`, `creator_handle`, and `creator_pane_key` were null for this depth-1 structured dispatch. Check the returned dispatch ID against the worker row because lookup is by task and retries/follow-ups can share a task. |
| `orca orchestration run-list --json --full`; `run-show --id <run_id> --json --full` | `runs[].id`, `runs[].coordinator_handle`, `runs[].consumer_generation`, `nextCursor`. All three run rows, including the legacy run, had null coordinator handles. `run-show` returned `run` and `removedWork`, with no current dispatch inventory. |
| `orca orchestration task-list --run <run_id> --json --full` | `runId`, `tasks[].id`, `run_id`, `parent_id`, `created_by_terminal_handle`, `created_by_pane_key`, `created_by_process_incarnation`, `status`. Unbound query without `--run` returned `run_required`. Task creation and dispatch creation can represent different actions. |
| `orca orchestration worker-show --dispatch <dispatch_id> --json --full` | Exact dispatch lookup with `dispatch.assigneeHandle`, `dispatch.creatorDispatchId`, `worker`, `projection`, `terminalResource`, `observation`, `coordinatedFrom`. The sampled structured response omitted creator session ID and had a null `terminal`. |
| `orca orchestration inbox --json --limit 100` | Without `--run` or `--terminal`, reads all mailboxes. The concise view exposes `messages[].type/from/to/handled/payload` and previews each body. `worker_done` means a report was sent. Mail was addressed to `run:run_<hex>` or `dispatch:ctx_<hex>`. `--full` exposes `from_handle/to_handle` and a JSON-encoded `payload` containing `taskId/dispatchId/outcome` on a sampled `worker_done`. Skip mailbox bodies in normal polling. |
| `orca terminal list --json`; `orca worktree list --json`; `orca status --json` | Terminal result was empty. Existing PTY integration uses `terminals[].handle/agentIdentity/preview/incarnationId/worktreePath`. Worktree rows include `id/path/projectId/identity.executionHostId` and worktree lineage. That lineage describes checkouts. Status provides `app/runtime/graph/caller`. |
| `orca worktree ps --json --limit 100` | `worktrees[].worktreeId/path/repo/hostId/agents[].paneKey` exposes live structured agent placement even with no PTYs. The coordinator matched a unique `structured-agent-session-<orca-session-id>:<pane-uuid>` row. `agents[].agentType/state/activity.status` give provider and turn hints. Use only metadata needed for linkage, since rows also contain prompt and reply previews. Follow the truncation indicator. |
| `orca --help`; `orca orchestration --help`; `orca agent-context [--json]` | Command discovery. The text agent-context points to the JSON schema. No orchestration watch or JSON stream was advertised. |

Full worker rows expose `dispatchId/taskId/runId/agentTerminalHandle/workerState/dispatchStatus/terminalState/coordinatedFrom` and `projection.{parent,provider,host,workspace,stage,outcome,liveness,evidence}`. All 51 rows had null `coordinatedFrom` and `projection.parent`. The four provider-populated rows identified Claude, Codex and Antigravity via `projection.provider.id`; all four had `provider.model` (e.g. `gpt-6.2-sol`). The other 47 rows had no provider model. `projection.workspace.id = <repo-uuid>::<checkout-path>` with `kind = folder_or_worktree` describes the worker's workspace. `resource.endpointIncarnation = structured:<orca-session-id>` and `resource.terminalHandle` expose runtime identity. For a reused resource, `resource.originDispatchId` and `resource.ownerDispatchId` can differ.

## Hook and process identity

A Windows `psutil.Process.environ()` probe of names containing claude, codex, node, gemini or antigravity found these Orca variable names (only identity values inspected for joins):

- `ORCA_AGENT_SESSION_ID`, `ORCA_TERMINAL_HANDLE`, `ORCA_STRUCTURED_SESSION`, `ORCA_APP_VERSION`, `ORCA_CLI_COMMAND`, `ORCA_CHAT_SCRATCH_DIR`, `ORCA_USER_DATA_PATH`, `ORCA_WSL_HOSTS_GATE_STATE`, `ORCA_CLAUDE_PROFILE_POINTER`, `ORCA_AGENT_SESSION_SPAWN_TOKEN`, `ORCA_ENVIRONMENT`, `ORCA_PAIRING_CODE`, `ORCA_REMOTE_PAIRING`.
- Structured Claude and Codex workers (and some Node helpers) inherited session UUIDs and `structworker_<uuid>` handles. This Codex worker's values exactly matched the dispatch assignee session ID and handle, the worker list handle, and the suffix of `resource.endpointIncarnation`. The coordinator's Claude/Node processes inherited `ORCA_AGENT_SESSION_ID = claude_<uuid_with_underscores>`, matching `dispatch.creator_orca_session_id`; those processes had no terminal handle. Strip the `orca_session_id:` address prefix only when normalizing an Orca CLI session address.
- No `ORCA_DISPATCH_ID`, `ORCA_TASK_ID`, `ORCA_RUN_ID`, `ORCA_SESSION_ID` or `ORCA_AGENT_PANE` appeared in the sampled processes. Earlier checked-in Orca PTY hook captures show `ORCA_AGENT_PANE = <uuid>:<uuid>` and `ORCA_TERMINAL_HANDLE = term_<uuid>`. No Gemini or Antigravity executable matched the live process filter. Some Claude, Codex and Node processes had no Orca variables. Multiple processes can share a session identity.

## Proposed integration

1. Add an orchestration inventory to the opt-in Orca pos. Poll full worker-list every **15 seconds** after the previous sweep completes, with timeout, backoff and last-good data on errors. Continue the existing PTY path for ordinary terminal agents. Cache full dispatch lookup by dispatch ID and refresh on a new dispatch, ownership change or unresolved parent, with bounded work per sweep. Use `worktree ps` on parent cache miss or periodically to resolve the coordinator session to its room, including when the hub has no matching hook session.
2. Send allowlisted `ORCA_AGENT_SESSION_ID` and `ORCA_TERMINAL_HANDLE` as optional Orca identity on Claude hook events, alongside the existing Claude session ID. Join on host plus Orca session ID to dispatch assignee, or use a matching handle with incarnation/owner validation. Use `dispatch.creator_orca_session_id` to find the coordinator's hook session and room. For nested workers, prefer a verified `creator_dispatch_id` edge and resolve the chain to its room. For PTY coordinators use an exact creator handle with matching incarnation where available. Keep unresolved workers in their known execution room or mark the parent unknown. A run ID groups dispatches but gives no direct proof of the creator's identity.
3. Create Orca worker records keyed by host and dispatch ID, using the projection provider and model for non-Claude avatars. Merge matching hook or PTY activity into the same avatar. Keep the execution checkout on the record even when the worker sits in the coordinator's room. Link these records separately from the Claude-native hook lifecycle in ADR-0028. Keep the coordinator's own status independent of worker activity.
4. Derive turn activity from `projection.stage.activity` and execution reachability from `projection.liveness.verdict` and freshness. A sample had `ready/dispatched/input_accepted/working` with `outcome=in_progress` and `liveness=live`; another had `succeeded/completed/settled/done` with `outcome=succeeded` while still live and retained. The latest sample also had `done/in_progress/live`. Use the dispatch outcome for settlement, and an exact `worker_done` message when report delivery itself matters. Retain settled avatars briefly, then expire them without equating a retained terminal with active work.

The Windows CLI took about 3–4 s for the 51-row full worker list, 2–4 s for run-list, 1–2 s for dispatch-show or inbox, about 1.4–2.4 s for worktree ps, and about 11 s for one empty terminal list. These are spot measurements including process startup. The sandbox denied access to the runtime; the live reads used approved escalation. Validate nested creators, historical or reused dispatch lookup, remote host boundaries, and a live Gemini/Antigravity process identity join with the same joins before relying on them across installations.
