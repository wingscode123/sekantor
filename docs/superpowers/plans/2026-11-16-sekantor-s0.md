# SeKantor S0 (rename, watch-only, activity) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the Ronda codebase into the SeKantor base: watch-only (no answering, no relay), events
carry a structured activity, every hook is asynchronous, and everything is named sekantor.

**Architecture:** Same Python hub, hooks and pos processes. Tasks 1-3 remove or add independent
slices and can run in parallel in separate worktrees; Task 4 (the rename) runs last on the merged result.

**Tech Stack:** Python 3.11, FastAPI, SQLite, Typer, pytest; React/Vite web UI (kept until S2).

**Spec:** `docs/superpowers/specs/2026-11-16-sekantor-design.md` (sections 3, 4, 8, 9 S0).

## Global Constraints

- Hooks fail closed and silently and never block an agent; after this plan every hook handler is `async`.
- Hub binds to 127.0.0.1 only; token required on every request; no outbound network calls from the hub.
- Windows, macOS and Linux.
- Conventional Commits, small; run the full test suite before each commit and commit only when the
  summary has no `failed` or `error`. Commit messages end with
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Each non-trivial decision gets an ADR in `docs/adr/` (template `0000-template.md`).
- Never run `uv sync`/`uv add` in `D:\Ronda` (the owner's hub runs from its `.venv`). In a worktree,
  `uv sync` creates that worktree's own `.venv`; run tests with `uv run pytest -q` there.
- Code, comments, commits and docs in English.
- The inbox web UI (`web/`) stays working, minus its answer buttons.

## Review Focus

1. An owner with the old install (hooks with `--wait`, sync PermissionRequest) runs the new code: the
   old handlers must not hang an agent and `doctor` must say "reinstall". (Task 2: test that
   `inspect()` flags a `--wait` handler as not current.)
2. An old client still POSTs an event with `capabilities` or a `request.id`: the hub accepts it (202)
   and ignores the answering parts. (Task 2: test.)
3. A tool name never seen before (an MCP tool `mcp__x__y`, a subagent `Task`) maps to `other`, never
   errors. (Task 3: test.)
4. The owner upgrades with `~/.ronda` present and a running Ronda service: first `sekantor up` copies
   token, config and database, and the old Ronda hooks are replaced, not duplicated. (Task 4: tests.)
5. `~/.sekantor` already exists when `~/.ronda` also exists: nothing is overwritten. (Task 4: test.)

- Modify behaviour:
  - `config.home()`: `~/.sekantor`, env `SEKANTOR_HOME`; `SEKANTOR_URL`, `SEKANTOR_PORT`,
    `SEKANTOR_PARENT_PID`, `SEKANTOR_PARENT_CREATED` replace the `RONDA_*` names. Database file `sekantor.db`.
  - `config.migrate_home(old: Path, new: Path) -> bool` (called by `sekantor up` and
    `sekantor install claude` before anything else): when `new` does not exist and `old` does, create
    `new`, copy `token` (mode 600), `config.toml`, `hosts.cache.json`, and the database
    (`ronda.db` → `sekantor.db` with `sqlite3.Connection.backup`, safe while a Ronda hub writes); return True.
    Never touches `old`; never overwrites anything in `new`.
  - `install.is_ours(handler)`: true for `sekantor-hook` and the old `ronda-hook`, so installing
    replaces Ronda's handlers instead of adding a second set.
  - `service.py`: `TASK = "SeKantor hub"`, `LABEL = "dev.sekantor.hub"`, unit `sekantor.service`;
    new field `Plan.cleanup: list[list[str]]` holds the old Ronda uninstall commands (`"Ronda hub"`,
    `dev.ronda.hub`, `ronda.service`); `service install` runs it first with `check=False`.
  - User-facing strings: "Ronda" → "SeKantor", `ronda` → `sekantor`.
